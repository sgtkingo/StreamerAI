# Title details and progressive episode search

Every tile opens the same detail overlay. A film shows its metadata, ratings, playback/library actions, and related films already validated in the local catalogue. Related results are deliberately not fabricated or fetched from an unvalidated remote source; they grow as the on-demand catalogue grows.

Series details use TMDB's deterministic season/episode structure. The live content coordinator remembers episode candidates verified during initial discovery, then searches missing episodes sequentially in the background through the configured media provider. Each candidate must match the title and exact season/episode marker, pass media inspection, and pass a just-in-time recheck before playback. Search work continues after the detail overlay closes. The detail API reports `searching`, `available`, or `unavailable` for each episode; the frontend polls only while the job is active. Already verified episodes remain playable while later episodes are still being searched.

The coordinator's active episode search and candidate map are currently process-local. Restarting the server restarts unfinished searches when the title is next due or explicitly requested; the canonical title, Library, and priority schedule remain in SQLite. Searches are sequential to limit provider load, so very large series can take time. A future durable job queue can replace the in-memory state without changing the provider-neutral detail contract. See [Availability search priority](AVAILABILITY_PRIORITY.md) for the current schedule.

The detail endpoint is `GET /api/v1/profiles/:profileId/titles/:titleId`. If a provider lookup fails, the UI can restart only missing episode lookups with `?retry=true`; verified episodes remain playable. Specific-episode playback uses `POST /api/v1/profiles/:profileId/playback/prepare` with `titleId`, `seasonNumber`, and `episodeNumber`. A request for a specific episode never falls back to a different episode; the coordinator checks parsed release markers again when rebuilding the candidate list.

## Multiple files for one title

`CatalogTitle.sources` contains a bounded, ranked list of distinct, inspected media files (`TitleSource`). Each source has a stable title-scoped ID, provider reference, release name, size, format hint, inspection timestamp and, for a series, exact season/episode. It contains **no direct playback URL**. The catalogue stores these references in SQLite as part of the canonical title, so a selected source survives a server restart. Duplicate provider references and duplicate release-name/size combinations are removed. The discovery pass inspects at most 12 matching candidates per title; this is a best-candidate shortlist, not an exhaustive scrape of the provider's entire catalogue.

The tile shows a source count and places a vertical three-dot button beside Play. The menu expands inside the tile, rather than opening an overlay that could be clipped or cover neighbouring cards. The same control is available in film details and beside an episode with multiple known files. Source rows show quality and language **hints** from file metadata; these are not promises about verified tracks. The first source is marked Recommended. Audio, subtitles and quality stay bound to the selected file. Escape closes the open menu; the tile menu also closes on an outside click.

Play without a selection retains automatic fallback across known candidates. Choosing a source sends its ID to `check` or `prepare`; the server resolves that ID only within the requested title and episode, reinspects the exact file and issues a normal single-source grant. It never silently falls back to a different file after an explicit selection. A failed alternative does not mark the whole title unavailable. The player remains bound to that one grant: switching files during playback, combining language or subtitle tracks across files, and saving provider direct links are deliberately out of scope.

Background series episode discovery still verifies only its first matching file per newly found episode and keeps that progressive search job in process memory. Expanding alternate sources for those later episodes, and persisting the full episode-source index at series scale, require a separate per-episode source repository rather than unbounded growth of `CatalogTitle.sources`.
