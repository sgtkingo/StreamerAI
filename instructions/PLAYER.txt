You are working on the StreamerAI project.

Your task is to audit and improve the current online media playback architecture, with primary focus on:

1. lazy / random-access loading of embedded subtitles,
2. discovery and loading of external subtitle files,
3. efficient HTTP Range usage against the remote media source,
4. preservation and improvement of the existing FFmpeg → fragmented MP4 browser playback pipeline,
5. reduction of redundant remote reads,
6. reproducibility, observability, caching, cancellation, and tests.

Do NOT blindly implement the design below.

First inspect the actual repository, understand the current architecture, compare it against this specification, identify discrepancies, and then implement the safest coherent solution.

==================================================
CURRENT EXPECTED ARCHITECTURE
==================================================

The current implementation approximately behaves as follows:

- Browser never receives the direct Webshare source URL.
- Browser receives a short-lived playback grant.
- Server resolves the remote source.
- Server verifies Range capability using a small byte-range request and expects HTTP 206.
- ffprobe discovers:
  - duration
  - video streams
  - audio streams
  - textual subtitle streams
- At least one video stream is required.
- First video stream is currently used.
- Server streams media through FFmpeg.
- Browser receives fragmented MP4.
- Input file is not fully downloaded.
- H.264 yuv420p/yuvj420p may be stream-copied.
- Other video is converted using libx264.
- Audio is normalized to AAC stereo.
- Approximate fragment duration is ~1 second.
- There is no browser-facing HTTP Range seek for the generated stream.
- Seek creates a new playback request starting at the selected timestamp.
- Audio stream changes also restart the media pipeline.
- Only one active media stream is currently allowed per playback context.
- Embedded textual subtitles are currently extracted in full to WebVTT.
- Extraction is asynchronous:
  - 202 while preparing
  - Retry-After for polling
- Extracted subtitle output is cached per grant/track.
- Subtitle extraction has limits such as:
  - ~10 minute timeout
  - ~8 MB output
- Local subtitle upload supports SRT/VTT/ASS/SSA.
- Image subtitles such as PGS/VobSub are currently not exposed.
- Full embedded subtitle extraction may perform a second complete/semi-complete remote pass and compete with video streaming for bandwidth.

Validate all of these assumptions against the real code.

==================================================
PRIMARY DESIGN GOAL
==================================================

Replace:

    embedded subtitle
        ↓
    extract entire subtitle track
        ↓
    wait
        ↓
    entire WebVTT
        ↓
    browser

with a lazy random-access model:

    current playback time T
        ↓
    request subtitle time window
        ↓
    demux only relevant source area
        ↓
    extract relevant subtitle packets
        ↓
    normalized subtitle cues
        ↓
    browser
        ↓
    prefetch next time window

The cost of obtaining subtitles after a seek should be proportional primarily to the local time region required for playback, NOT to the total movie duration.

Do NOT implement a custom Matroska/EBML parser unless absolutely necessary.

Prefer FFmpeg/libavformat functionality.

Matroska Cues / container indexes and HTTP byte seeking should be delegated to FFmpeg where possible.

TARGET ARCHITECTURE
==================================================

Target conceptual architecture:

Browser
  │
  ├── GET playback manifest
  │       ↓
  │   ProbeService
  │
  ├── GET media stream?start=T&audio=N
  │       ↓
  │   PlaybackMediaEngine
  │       ↓
  │     FFmpeg
  │       ↓
  │      fMP4
  │
  └── GET subtitle window
          ↓
      SubtitleService
          │
          ├── EmbeddedSubtitleProvider
          │       ↓
          │   FFmpeg/libavformat
          │   timestamp seek
          │
          └── ExternalSubtitleProvider
                  ↓
              SRT/VTT/ASS parser

All normalized to:

interface SubtitleCue {
    startMs: number;
    endMs: number;
    text: string;
    settings?: string;
}

interface SubtitleWindow {
    trackId: string;
    startMs: number;
    endMs: number;
    cues: SubtitleCue[];
}

The frontend must not care whether subtitles originated from:

- embedded SubRip
- embedded ASS/SSA
- WebVTT
- mov_text
- TTML
- external SRT
- external VTT
- external ASS/SSA

Container-specific behavior belongs server-side.

PHASE 4 — LAZY EMBEDDED SUBTITLE EXTRACTION
==================================================

Implement an API similar to:

GET /api/playback/:grant/subtitles/:trackId/window
    ?start=<seconds-or-ms>
    &duration=<window-duration>

Choose one consistent unit across API types.

Milliseconds internally are preferred.

Recommended default subtitle window:

120 seconds

Make the window duration configurable.

Apply sane min/max limits.

Example:

requested:
    start = 4,980,000 ms
    duration = 120,000 ms

returns cues overlapping:

    [4,980,000 ; 5,100,000]

Important:

Include cues that START before the requested window but are still active at startMs when feasible.

For example:

cue:
    4979.0 → 4983.0

request:
    4980.0 → 5100.0

The cue should be included because it overlaps the requested interval.

==================================================
FFMPEG EXTRACTION BEHAVIOR
==================================================

Use FFmpeg/libavformat timestamp seeking.

Do NOT sequentially process the complete file from t=0.

Verify empirically that the resulting FFmpeg invocation performs remote seeking when the input supports HTTP ranges.

Use appropriate input-side seeking.

Be careful about the semantic difference between:

    -ss before -i

and:

    -ss after -i

For remote random access, prefer input seeking when compatible.

The extraction process should:

1. start near the requested timestamp,
2. select only the requested subtitle stream,
3. avoid transcoding unrelated video/audio,
4. stop shortly after the requested end timestamp,
5. produce either:
   - WebVTT
   - or another easily parsed textual representation,
6. normalize result to SubtitleCue[].

Do not let FFmpeg run until EOF.

Do not decode video/audio merely to obtain subtitle text.

Use explicit stream mapping.

Example conceptual behavior:

ffmpeg
    input seek ~start
    input remote URL
    map subtitle track N
    limit duration
    subtitle conversion
    output pipe

Derive the exact safe command based on the currently supported FFmpeg version.

Do not copy this pseudo-command blindly.

==================================================
SEEK ACCURACY
==================================================

Timestamp seek may land before the exact requested time due to container indexing.

This is acceptable and expected.

The service must:

- parse resulting cues,
- normalize timestamps to absolute movie timestamps,
- filter by interval overlap,
- avoid duplicate cues,
- tolerate FFmpeg returning some cues before requested start.

Pay special attention to whether FFmpeg resets timestamps when using:

- -ss
- -copyts
- -start_at_zero
- output WebVTT

Write explicit tests for timestamp normalization.

Do not ship a solution that returns window-relative timestamps if the frontend expects movie-relative timestamps.

==================================================
SUBTITLE CACHE
==================================================

Add a dedicated cache.

Cache key should represent at least:

- immutable/stable media identity
- subtitle track
- normalized time window
- subtitle conversion version/settings

Prefer media identity over grant identity when security semantics allow this.

A grant can expire while cached subtitle data remains valid for the same immutable media object.

Do not cache against URL strings if the remote URL is ephemeral.

Possible key concept:

mediaId
+ mediaVersion
+ subtitleTrack
+ windowStart
+ windowSize
+ converterVersion

Use deterministic aligned windows.

For example with 120 s windows:

0–120
120–240
240–360
...

If client asks for t=170:

serve/cache:

120–240

This gives significantly better cache reuse than arbitrary:

170–290

If necessary return the canonical actual window boundaries.

Cache can initially be in-memory, but design the abstraction so persistent/distributed caching can be added later.

Respect global memory limits and eviction.

==================================================
FRONTEND SUBTITLE PREFETCH
==================================================

Implement client-side window management.

Recommended model:

previous window
current window
next window

Example:

current playback = 1250 s
window size = 120 s

loaded roughly:

1080–1200
1200–1320
1320–1440

Prefetch the next window before entering it.

For example:

at ~75–85% of current window:
    start fetching next window.

Do NOT poll current playback every 100 ms merely to determine whether a subtitle cue exists if there is a cleaner event-based/render-loop implementation already available.

Reuse existing rendering architecture when practical.

==================================================
SEEK BEHAVIOR
==================================================

When user seeks:

1. abort obsolete subtitle requests,
2. clear irrelevant prefetch state,
3. calculate target canonical subtitle window,
4. request it immediately,
5. optionally request next window,
6. let video seek happen independently.

Video and subtitle seek should run concurrently.

Do not serialize:

    video seek
    then subtitle seek

unless a real synchronization requirement exists.

Use AbortController or the project's existing cancellation abstraction.

Old subtitle requests must not overwrite state after a newer seek.

Protect against races using:

- request generation id
- AbortSignal
- sequence/token validation

==================================================
AUDIO SWITCH
==================================================

Do not redesign the full media transport solely for this task.

However:

- ensure subtitle state survives an audio-only stream restart,
- do not unnecessarily re-download subtitle windows,
- preserve current playback time,
- cancel only processes/resources that need cancellation.

==================================================
HTTP RANGE VALIDATION
==================================================

Improve current source capability probing.

Do not rely solely on Accept-Ranges header.

A real request such as:

Range: bytes=0-0

with valid:

206 Partial Content
Content-Range: bytes 0-0/TOTAL

is stronger evidence.

Validate Content-Range.

Store:

- supportsRange
- contentLength
- ETag
- Last-Modified where available

Handle servers that:

- ignore Range and return 200,
- return malformed Content-Range,
- use unknown total size,
- expire signed URLs.

Fail gracefully.

==================================================
REMOTE URL EXPIRY
==================================================

Do not use an expiring direct URL as long-lived cache identity.

The service should be able to reacquire/refresh the remote source URL from the grant/source abstraction when required.

A new subtitle window request several minutes later must not fail solely because an old internally cached signed URL expired, if the underlying grant/media authorization remains valid.

Reuse the project's existing security model.

Never expose source URL to the browser.
